## Authentication
- The reviewed route pages consistently require a `key` parameter described as either an `API license key` or `FraudLabs Pro API key`.
- The reviewed docs present auth as a request parameter, not as a bearer-token or custom-header scheme.
- GET routes document `key` alongside the query parameters.
- POST route examples often show `Content-Type: application/json`, but the auth value is still part of the submitted request payload.

## Common request / response conventions
- Base URL: `https://api.fraudlabspro.com/v2`
- Response format is controlled per route by the optional `format` parameter.
- The reviewed route pages repeatedly document `json` as the default format and `xml` as the alternative.
- Fraud-screening routes return large nested result objects; the reviewed response tables expose fields such as `ip_geolocation.*`, score/status outputs, and reason arrays.
- The reviewed docs do not describe any cursor, page-number, or token pagination model for these routes.

## Manually confirmed endpoint set

### 1) Screen Order
- Method: `POST`
- Path: `/order/screen`
- Full URL: `https://api.fraudlabspro.com/v2/order/screen`
- Purpose: screen an order transaction for payment fraud
- Required parameters directly confirmed on the official page:
  - `ip` - transaction IP address; IPv4 and IPv6 supported
  - `key` - API license key
- Optional parameters directly confirmed on the reviewed page include:
  - `format` - `json` or `xml`; defaults to `json`
  - `last_name`, `first_name`
  - `bill_to`, `bill_addr`, `bill_city`, `bill_state`, `bill_country`, `bill_zip_code`
  - `ship_last_name`, `ship_first_name`, `ship_addr`, `ship_city`, `ship_state`, `ship_country`, `ship_zip_code`
  - `user_phone`, `email`, `email_hash`, `email_domain`, `username`
  - `bin_no`, `card_hash`, `avs_result`, `cvv_result`
  - `user_order_id`, `amount`, `quantity`, `currency`, `department`
  - `payment_gateway`, `payment_mode`, `coupon_code`, `flp_checksum`
- Important official notes:
  - `bill_country` and `ship_country` use ISO-3166 alpha-2 country codes
  - `currency` uses ISO-4217 3-character currency codes
  - `payment_mode` values shown on the page: `creditcard`, `paypal`, `cod`, `bankdeposit`, `giftcard`, `crypto`, `wired`, `others`
  - `flp_checksum` is tied to FraudLabs Pro's `Agent JavaScript` helper for device validation
- Response highlights directly confirmed on the reviewed response table:
  - extensive `ip_geolocation.*` metadata
  - risk / scoring fields beyond the truncated sample table, indicating a much larger fraud-analysis response object

### 2) Feedback Order
- Method: `POST`
- Path: `/order/feedback`
- Full URL: `https://api.fraudlabspro.com/v2/order/feedback`
- Purpose: send post-review feedback for an existing screened order
- Required parameters:
  - `id` - unique transaction ID generated by the Fraud Check API
  - `key` - API license key
  - `action` - review outcome
- Optional parameters:
  - `format` - `json` or `xml`; defaults to `json`
  - `note` - notes for the feedback request
- Official action values listed on the request page:
  - `APPROVE`
  - `REJECT`
  - `REJECT_BLACKLIST`
- Important doc note:
  - the prose summary mentions `IGNORE`, but the request parameter table only enumerates `APPROVE`, `REJECT`, and `REJECT_BLACKLIST`; the parameter table is the more concrete contract surface reviewed in this pass
- Confirmed response field:
  - `fraudlabspro_id` - the FraudLabs Pro transaction ID that was updated

### 3) Get Order Result

- Full URL: `https://api.fraudlabspro.com/v2/order/result`

### 4) Screen User
- Method: `POST`
- Path: `/user/screen`
- Full URL: `https://api.fraudlabspro.com/v2/user/screen`
- Purpose: screen a user transaction for account-takeover fraud
- Required parameters:
  - `key` - API license key
  - `email` - user's email address
  - `ip` - user's IP address; IPv4 and IPv6 supported
- Optional parameters:
  - `format` - `json` or `xml`; defaults to `json`
  - `flp_checksum` - device-validation checksum from Agent JavaScript
  - `last_name`, `first_name`, `phone`
- Confirmed response fields:
  - `user_score` - integer 1 to 100 risk score
  - `user_transaction_id` - unique ID for this screen call
  - `user_transaction_status` - `APPROVE`, `REJECT`, or `REVIEW`
  - `reason` - array explaining reject/review outcomes

### 7) Send SMS Verification
- Method: `POST`
- Path: `/verification/send`
- Full URL: `https://api.fraudlabspro.com/v2/verification/send`
- Purpose: send an SMS containing an OTP and custom verification message
- Required parameters:
  - `tel` - recipient phone number in E.164 format
  - `key` - FraudLabs Pro API key
  - `mesg` - message template; must include `<otp>` placeholder
- Optional parameters:
  - `country_code` - ISO 3166 country code for the recipient phone number
  - `otp_timeout` - OTP validity in seconds; default `3600`, min `15`, max `86400`
  - `format` - `json` or `xml`; defaults to `json`
- Important official notes:
  - message length max is `140` characters
  - the page says the input must be encoded the same way as data posted from a WWW form, i.e. percent-encoded form data
  - users should confirm sufficient SMS credits before sending
  - a `24 hours` cooldown applies if SMS delivery fails `10` times in one day
- Confirmed response fields:
  - `tran_id` - 20-character unique ID for the verification transaction
  - `credits_remaining` - remaining SMS credits
- Sandbox notes directly confirmed on the page:
  - `+11` simulates successful SMS sending without deducting credits
  - OTP `123456` can then be used for successful verification in sandbox mode
  - `+11234` returns an `Invalid phone number` error

### 8) Get Verification Result
- Method: `GET`
- Path: `/verification/result`
- Full URL: `https://api.fraudlabspro.com/v2/verification/result`
- Purpose: verify whether a submitted OTP matches a valid SMS verification transaction
- Required parameters:
  - `key` - FraudLabs Pro API key
  - `tran_id` - unique ID returned by the send-verification route
  - `otp` - one-time password submitted by the recipient
- Optional parameters:
  - `format` - `json` or `xml`; defaults to `json`
- Confirmed response field:
  - `result` - `Y` for a valid OTP match, `N` when no valid OTP is found

### 9) Feedback Payment
- Method: `POST`
- Path: `/payment/feedback`
- Full URL: `https://api.fraudlabspro.com/v2/payment/feedback`
- Purpose: report final payment-gateway outcome back to FraudLabs Pro
- Required parameters:
  - `key` - API license key
  - `email` - email address of the payment order
  - `status` - payment-order status
  - `message` - gateway response message for the payment order
- Optional parameters:
  - `fraudlabspro_id` - unique transaction ID generated by Fraud Check API
- Confirmed response field:
  - `result` - result returned from the payment-feedback API

## Pagination
- None of the reviewed FraudLabs Pro routes document pagination.
- Each route is a single request / single response transaction rather than a list endpoint.

## Rate limits and plan notes
- The reviewed route pages do not publish a general numeric API rate-limit table.
- Explicit usage / access limits confirmed in this pass:
  - `Get Order Result` is limited to paid plans and excludes the Micro plan
  - `Get User Result` is limited to Medium plan and above
  - `Send SMS Verification` requires available SMS credits
  - `Send SMS Verification` enforces a 24-hour cooldown after 10 failed deliveries in one day
- The validation-rules page says there are more than `100` validation rules and instructs readers to use the pricing page to see how many rules are available per plan.

## Error handling
- The reviewed route pages are stronger on required-field definitions than on shared HTTP status-code tables.
- Confirmed error-related behavior from the official pages reviewed in this pass:
  - request validation is driven by required parameter contracts and the separate validation-rules catalog
  - the SMS sandbox explicitly documents an `Invalid phone number` error outcome for `+11234`
  - OTP verification returns `Y` or `N` rather than a paginated status resource
- The docs navigation includes a dedicated `Error Codes` reference page, indicating a provider-level error-code catalog exists, but the route pages reviewed in this pass did not expose a shared HTTP error matrix directly.

## Response format notes
- JSON is the documented default response format across the reviewed routes.
- XML is consistently offered as an alternative via the `format` parameter.
- POST examples for several routes use `Content-Type: application/json`, while the SMS send page also includes an explicit form-encoding note.

## Important usage notes
- FraudLabs Pro's reviewed public API surface spans three sub-domains of functionality in one base URL family: order fraud screening, account-takeover screening, and SMS verification.
- The order and user retrieval routes are plan-gated; do not assume all accounts can read back historical screening results.
- The validation-rules reference is an important companion document because it explains the rule library that powers order and user decisions.
- A few reviewed example blocks contain small inconsistencies versus the request tables, so implementers should trust the request line and parameter table first when sample code conflicts.
