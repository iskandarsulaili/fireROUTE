# Telegram Bot

## Provider metadata
- Category: `Social`
- Provider slug: `telegram-bot`
- Official docs pages used:
  - `https://core.telegram.org/bots/api`
- Main API base URL: `https://api.telegram.org`
- Method-call base pattern: `https://api.telegram.org/bot{token}/{methodName}`
- File-download base pattern: `https://api.telegram.org/file/bot{token}/{file_path}`
- Auth model: bot token embedded in the request path
- Supported request methods: `GET`, `POST`
- Supported request payload formats: URL query string, `application/x-www-form-urlencoded`, `application/json` (except file uploads), `multipart/form-data`
- Response format: JSON envelope with `ok`, `result`, `description`, `error_code`, and optional `parameters`
- Manually confirmed route count: `176`

## Authentication
- The official page says each bot gets a unique authentication token when it is created.
- Every request uses that token directly in the URL path rather than in an Authorization header.
- The docs show the canonical format as `https://api.telegram.org/bot<token>/METHOD_NAME`.
- All requests must use UTF-8.

## API-wide behavior
- All Bot API requests must be served over HTTPS.
- All methods are case-insensitive.
- Telegram supports two mutually exclusive update-delivery modes:
  - polling via `getUpdates`
  - webhooks via `setWebhook`
- Incoming updates are stored on Telegram's servers for up to `24` hours.
- Update payloads are JSON-serialized `Update` objects.

## Response envelope
- Success responses return `ok: true` and a `result` field.
- Failure responses return `ok: false` and include `description`.
- The docs say an integer `error_code` may also be returned.
- Some errors also include `parameters` of type `ResponseParameters` to help with automated recovery.

## Canonical endpoint patterns

### 1) Call any Bot API method
- Method: `GET` or `POST`
- Path pattern: `/bot{token}/{methodName}`
- Purpose: invoke one of the documented Bot API methods

### 2) Download a file after `getFile`
- Method: `GET`
- Path pattern: `/file/bot{token}/{file_path}`
- Purpose: download a file using the `file_path` returned by `getFile`
- Important note: the docs say download links are valid for at least `1` hour and can be regenerated by calling `getFile` again

## High-value method details

### `getUpdates`
- Route: `GET` or `POST` `/bot{token}/getUpdates`
- Purpose: long-poll for incoming updates
- Parameters:
  - `offset` - optional update cursor; can also be negative to read from the tail of the queue
  - `limit` - optional `1-100`, default `100`
  - `timeout` - optional long-poll timeout in seconds
  - `allowed_updates` - optional JSON-serialized list of update types
- Usage notes:
  - does not work while a webhook is active
  - the docs recommend recalculating `offset` after each response to avoid duplicates

### `setWebhook`
- Route: `GET` or `POST` `/bot{token}/setWebhook`
- Purpose: configure outgoing webhook delivery
- Parameters:
  - `url` - required HTTPS URL; empty string removes the webhook
  - `certificate` - optional uploaded public key certificate for self-signed setups
  - `ip_address` - optional fixed delivery IP override
  - `max_connections` - optional `1-100`, default `40`
  - `allowed_updates` - optional JSON-serialized list of update types
  - `drop_pending_updates` - optional boolean
  - `secret_token` - optional `1-256` chars; sent as `X-Telegram-Bot-Api-Secret-Token`
- Usage notes:
  - while a webhook is active, `getUpdates` cannot be used
  - Telegram retries failed webhook deliveries for a reasonable number of attempts

### `getWebhookInfo`
- Route: `GET` or `POST` `/bot{token}/getWebhookInfo`
- Purpose: inspect current webhook state and delivery problems

### `sendMessage`
- Route: `GET` or `POST` `/bot{token}/sendMessage`
- Purpose: send a text message
- Important parameters confirmed on the official page:
  - `chat_id` - required target chat or `@username`
  - `text` - required message text, `1-4096` characters after entity parsing
  - `message_thread_id` - optional forum topic target
  - `direct_messages_topic_id` - optional direct-messages topic identifier
  - `parse_mode` or `entities` - optional formatting controls
  - `link_preview_options` - optional link preview config
  - `disable_notification` - optional silent delivery flag
  - `protect_content` - optional anti-forward/save flag
  - `allow_paid_broadcast` - optional paid high-throughput delivery toggle
  - `reply_parameters` - optional reply metadata
  - `reply_markup` - optional inline/custom keyboard payload

### `getFile`
- Route: `GET` or `POST` `/bot{token}/getFile`
- Purpose: resolve a `file_id` into downloadable file metadata
- Parameters:
  - `file_id` - required file identifier
- Usage notes:
  - the hosted Bot API currently allows bots to download files up to `20 MB`
  - the official download URL format is `/file/bot{token}/{file_path}`
  - the docs warn that original filename and MIME type may not always be preserved here

## Rate limits, throughput, and file-size notes
- By default, the docs say bots can broadcast up to `30 messages per second`.
- The docs say `allow_paid_broadcast=true` can raise throughput to `1000 messages per second` for a fee of `0.1 Telegram Stars` per successful message.
- `getUpdates.limit` accepts `1-100` and defaults to `100`.
- `setWebhook.max_connections` accepts `1-100` and defaults to `40`.
- Hosted Bot API file downloads are limited to `20 MB` via `getFile`.
- The official method pages say bots can currently send many uploaded media/file types up to `50 MB`.
- The same official page says sending existing Telegram-hosted files by `file_id` has no upload-size limit because the file is not reuploaded.

## Local Bot API server notes
- The official page says Telegram publishes the Bot API server source code and lets you run your own server.
- The documented advantages of a local Bot API server include:
  - download files without a size limit
  - upload files up to `2000 MB`
  - upload by local path or `file:` URI
  - use an HTTP webhook URL
  - use any local IP address and any port for webhooks
  - set `max_webhook_connections` up to `100000`
  - receive absolute local `file_path` values after `getFile`

## fireROUTE normalization notes
- Preserve the Bot API response envelope instead of flattening away `ok`, `description`, `error_code`, or `parameters`.
- Treat the path token as part of authentication, not a normal resource identifier.
- Model `/file/bot{token}/{file_path}` separately from `/bot{token}/{methodName}` because download behavior and expiry semantics differ.
- Do not invent a global pagination abstraction for this provider; update retrieval and list-style methods use method-specific `offset`, `limit`, cursor, or chat-scoped semantics.
